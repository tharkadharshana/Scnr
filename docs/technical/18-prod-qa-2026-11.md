# Production QA run, 2026-11-14

An end-to-end pass over https://scnr.tharkak.com, driven by an AI agent that clicked the real UI in a real Chrome window, logged in as the owner (Business plan, granted by hand). Repo state tested: `main` at `041eef8` (PRs #92 to #102, the data-contract project). Billing was out of scope.

This document records what was tested, what passed, what is broken, and what was not covered. Every bug below has a reproduction. Nothing in the app was changed by this run; all test data was deleted at the end (see "Cleanup").

## How the run worked

- A separate Chrome window with a clean profile, remote-controlled with Playwright over the Chrome DevTools protocol. The owner logged in to Google once by hand. No credentials were shared with the agent.
- Real clicks, typing and navigation through the UI. API calls were used only where a person cannot see the result (reading saved data, API v1 checks, scan counts).
- Scans were simulated with real mobile-emulated browser tabs and `curl` using a different User-Agent per request (the visitor guard is keyed on IP plus User-Agent, so repeating one User-Agent hides redirects behind HTTP 429).
- QR images were downloaded from the app and decoded again with the app's own scanner tool, so the printed code is proven to point at the right slug.
- Personas used: **Nimal** (tea shop owner, never heard of "dynamic QR", Android phone), **Dilini** (restaurant manager: menu, orders), a **marketer** (campaign links, pages, forms, API).
- A background code reviewer read the diff of PRs #92 to #102. Its findings are listed separately and marked "static review, not reproduced".

## P1: break a promise the product makes

### 1. "Swap today's offer" does nothing (data-contract regression)

- **Repro:** Dashboard, a Restaurant Kit card, Offer, type text, Make live. A green toast says "Offer is live on the next scan. No reprint needed." `PUT /api/qr/<slug>` returns 200. Read the code back: the blocks are still just `header` and `menu`. The offer is gone.
- **Cause:** `src/components/OfferSwap.tsx` line 15 writes the old flat shape `content_data.offer = { text }`. Since the contract PRs (#94, #95) the server keeps an offer only as an `offer` block inside `content_data.blocks` and drops unknown keys (`src/lib/contracts/restaurant.ts`, `page.ts`). It affects kits and pages.
- **Fix:** In `OfferSwap`, find the block with `kind === 'offer'` in `content_data.blocks` and set its `text`, or append one. Remove the empty case by deleting the block. Add a `tests/qa.ts` check that a PUT of an offer block round-trips and that the guest page shows it.
- **Proof the block itself renders:** adding an `offer` and a `wifi` block through API v1 was accepted and, after the cache cleared, both showed on the guest page.

### 2. Edits (and deletes) can take minutes to reach scanners

- **Repro:** Edit a code's destination in the UI. The dashboard updates at once. The redirect kept serving the old URL for more than 3 minutes while it was being scanned every 10 to 20 seconds. A second run went live after about 50 seconds. A kit edit (offer and Wi-Fi blocks via API) stayed stale for over 5 minutes while scanned every 12 seconds, then appeared after 6 quiet minutes. Two deactivated-then-scanned codes still answered HTTP 410 after being deleted, instead of 404; one deleted short link still redirected minutes later.
- **Likely cause:** `worker/worker.js` lines 360 to 366 re-write the cached config (TTL 300 s) on any scan once a minute. A colo that read a stale copy can write it back after the owner's purge, which resurrects the old data. `purgeEdge` in `server/index.ts` line 382 is best effort and swallows errors, and KV deletes take up to 60 seconds to spread.
- **Why it matters:** the busier the cafe, the longer an edit can stay hidden. This is the opposite of "change your menu, offer or Wi-Fi any time".
- **Fix ideas:** do not re-put a config that was only read; or store the code's `updated_at` in the cached config and have the purge write a short-lived version key that the Worker compares; log purge failures instead of swallowing them.

### 3. The default visitor guard blocks real guests

- **Repro:** every new code is created with "5 scans per visitor per 3600 seconds" (`CreateQR.tsx` line 110, `server/index.ts` line 1790). Free plans cannot change it (`visitor_guard_gate`). A visitor is `sha256(CF-Connecting-IP + User-Agent + day + salt)` (`worker.js` line 147). Spaced requests from one IP and User-Agent got HTTP 429 after the fifth.
- **Why it matters:** guests on one cafe Wi-Fi, or on a mobile carrier's shared address, with the same phone model, share one visitor. The sixth guest in an hour could be refused on a menu QR. Enforcement is fuzzy (rapid bursts passed), so this is a risk estimate, not a measured failure rate.
- **Fix ideas:** default to unlimited (0) for new codes and make the guard opt-in; or raise it a lot for restaurant kits; and show a plain page text when it triggers.

### 4. WhatsApp numbers typed the Sri Lankan way produce a broken link

- **Repro:** a WhatsApp code, or `/tools/whatsapp-link`, with `0771234567`. The link becomes `https://wa.me/0771234567`. WhatsApp needs `94771234567`.
- **Cause:** `waLink()` in `src/lib/site.ts` strips non-digits and nothing more. The placeholder shows `+94 77 123 4567`, but people type `077...`.
- **Fix:** treat a leading `0` as Sri Lanka (`94`). Add an assert to the self-check at the bottom of `qrContent.ts`.
- Related, lower impact: Phone and SMS codes keep `0771234567` (fine in Sri Lanka, wrong abroad).

### 5. Sign-in shows a raw Supabase domain, and Google is the only way in

- **Repro:** anonymous visitor, "Start free trial". The Google screen says "to continue to noqstzknowdtpsiafdxw.supabase.co". There is no Scnr name. A non-technical user can read that as a scam.
- **Fix:** a Supabase custom auth domain and branding on the Google OAuth consent screen (steps are in doc 12). Email sign-up (PR #54) is still held, so people without a Google account cannot register.
- The same raw Supabase domain is what a visitor sees for PDF codes (the redirect goes to `...supabase.co/storage/v1/object/public/files/<uid>/<uuid>.pdf`).

### 6. Restaurant Kit templates give the wrong defaults

- Choosing a template flips the currency to **USD** (`Kit.tsx` line 181), so guests see `$10` and `$6`. The currency select is on step 3 and easy to miss. The owner's order stats also show `$`.
- The `boba-1` design hard-codes a **"Table 4"** chip and a **"$6"** starburst on the hero (`src/lib/kitDesigns/boba-1.ts`). Every guest sees them whatever the menu holds. Other designs were not checked for hard-coded sample text.

## P2: wrong or confusing, but the work still gets done

7. **Scan numbers disagree.** For a PIN-protected code, "Total scans" was 2 while "Recent Scans", the Live Scan Stream and the CSV listed 7 rows. PIN-page views and blocked attempts are stored as scan events. Some rows have an unknown city. The CSV has no city column although the page shows cities.
8. **Dashboard counts disagree.** The stat card said "QR Codes 12"; the filter chips said "All 15 = 8 + 3 + 3 + 1". Settings said "4 / 2000" while Admin Customers said "3/2000 dynamic" and "6 codes". "Scans this month" also differed between pages. Decide one definition per number and use it everywhere.
9. **Google review codes accept any Place ID.** `abc` goes straight through. Real IDs start with `ChIJ`. A typo prints a dead QR.
10. **Past expiry dates are accepted.** The date field has no minimum; the code was created already expired and scanning it showed "QR expired".
11. **After "Create page" the user lands on the template gallery**, not on their page or its QR. The page is under Pages, then "Your pages". `/pages/new` with no template silently redirects to the gallery. "Load from template" on Create QR opens that same page gallery, which is not what the label suggests.
12. **API keys are inside the "Members" tab**, but the API docs say "Settings, then API keys". The Settings quick links (Workspaces, Members, Custom domains, Webhooks) are tabs under a row of links, which is hard to read.
13. **Stale lists in Settings.** A new workspace shows "0 of 10" and no row until reload; a deleted webhook stays listed until reload; the Webhooks heading shows "0 of" with the limit missing.
14. **"Upgrade" shows on the top plan.** The Dashboard plan card says BUSINESS next to "Upgrade".
15. **Date formats vary** (`11/14/2026`, `10-16`, `10/22/2026`). Month-first is ambiguous for Sri Lankan readers; add the month name.
16. **Zip file names drop non-Latin letters.** `QA-bulk සිංහල` became `QA-bulk_.svg`. Two Sinhala titles would collide. The ZIP holds SVG only.
17. **Order bar grammar:** "1 items", "From the 1 orders loaded".
18. **AI is off in production** (`Create with AI` and `Import your menu` are hidden because `/api/ai/usage` reports disabled). Not tested. Decide whether to switch it on.

## P3: small things

- The Smart Routing and Visitor Guard panels appear on every wizard step (Content, Style, Options, Review), which is a lot for a first-time user. They fit only on the Content or Options step.
- Link-check warning "Page not found (404). Save anyway?" is good. Bulk errors say `destination_url must be a valid URL`, which is API wording.
- The guest order form validates the name only after a server round trip (about a second), no client-side check.
- Header title shows "Das..." at about 1100 px wide. Fine at 1920 px.
- Many tap targets under 32 px on the mobile dashboard (29 on one screen).
- Public `/tools` pages show "Sign in" and "Sign up free" to a signed-in user.
- vCard files include empty `ORG:` and `URL:` lines. The Location code ignores the typed place name. LinkedIn handles always use `/in/`.
- Template previews log "Blocked script execution in about:srcdoc" on `/pages`, `/kit`, `/forms/new` (sandboxed iframe without `allow-scripts`). Harmless but noisy.
- The dashboard never reaches network idle (the real-time stream keeps a connection open); fine for users, awkward for test tools.
- Unknown routes inside the app show the branded "QR not found" page.

## Static review of PRs #92 to #102 (not reproduced; needs a Free account or old data)

A read-only reviewer found these. They need a Free plan user or pre-migration data to confirm, so treat them as leads.

- **Free users cannot save older pages** whose theme maps to a Pro design (nine of the 20 templates are Pro-only): `server/index.ts` lines 2100 to 2157 return 403 `FEATURE_DESIGN` when only a text block changed.
- **Free users lose their Kit wizard work** when they pick a Pro Kit design (`Kit.tsx` line 249 navigates to billing on 403). The wizard and the page and form editors show no Pro marker; the template gallery gives no lock sign.
- **A Free user can get a Pro page design** through a restaurant row with `design = NULL` and `content_data.design` set (`server/index.ts` lines 2145 to 2159).
- **Old restaurant pages that break the new contract** (header not first, two Wi-Fi blocks, a products block, more than 40 blocks) are refused on save with `INVALID_RESTAURANT`.
- **A page with a custom theme loses its look on the first save** (the theme collapses to the default plus an accent).
- **Converting an old flat Kit page** leaves it as a restaurant with no menu and opens the Kit wizard on it.
- **`if_updated_at` is checked, then the update runs separately**, and only the Orders page sends it, so two tabs saving the same page is last-write-wins.
- Smaller items: stale `design` after changing type through the API, `by_design` and `funnel` loops that are quadratic, `guest_events` rows with no cap until the 90-day cleanup, and `rules` silently dropped from a page PUT.
- The reviewer found no ownership (IDOR) or injection problem and confirmed that bulk and API v1 go through the same Pro gate.
- Deploy reminder from the reviewer: the Worker imports `src/lib/guestPage`, so every guest-page change only reaches scanners after `cd worker && npx wrangler deploy`. The `worker.js` file itself did not change in these PRs, so the need is easy to miss.

## What passed, in detail

- **Scanning:** a mobile-emulated Chrome tab and `curl` both reached the destination, and the dashboard stream showed the new scan with city, device, browser and Sri Lanka time. Every code type produced the right result: URL, Wi-Fi page with a copy button (special characters kept), vCard download, WhatsApp, Phone `tel:`, SMS `sms:`, Location, Event `.ics`, Email `mailto:`, App store (picked by device), Text, PDF, GS1, and the six social handle types.
- **Gates:** wrong PIN shows "Incorrect PIN", brute force returns 429 "Too many attempts" and clears within a minute, the scan limit returns 410 and flips the card to Paused, a past expiry returns 410 "QR expired", bulk Deactivate returns 410 at once.
- **Scan hygiene:** WhatsApp and Facebook previews, Googlebot and HEAD requests redirect but are not counted; a prefetch header gets 503; one real scan counted.
- **Forms:** native required checks, honeypot field present, thank-you text, responses with status buttons and CSV, and `<script>` text stored and shown as text.
- **Orders:** add to cart, dine-in or takeaway, table, name and phone, order code, and the owner board moving an order through Accept, Mark paid, Start cooking, Mark ready and Mark served; HTML in the note is stripped.
- **Tools:** the QR generator's PNG decoded by the scanner tool to the exact URL; the dashboard's PNG decoded to the correct slug; a code with a busy image as its logo still scanned.
- **API:** key shown once, revoke works (401 afterwards), bad and missing keys 401, create, update and delete work, invalid destination 400, a code with a PIN exposes `has_password` only.
- **Webhooks:** non-https rejected, secret shown once, delete asks first.
- **Safety copy:** delete and bulk delete dialogs say the scan data goes with the code and that printed codes will stop working.

## Cleanup

All QA objects created through the UI were deleted at the end of the run: 14 extra-type codes, the Wi-Fi, WhatsApp, vCard, URL, gated, routing, expiry, styled and PDF codes, a Restaurant Kit with its order, a page, a form with its response, and the QA short links. The QA API key was revoked and the QA webhook deleted.

Left behind, for the owner:

- A workspace named **QA-Workspace** (there is no delete control in the UI). Remove it in the Supabase table `workspaces`.
- One short link, `qa-short-36590`, was deleted in the app but still redirected for a few minutes afterwards because of the edge cache problem in P1 item 2. It returned 404 at the end of the run.
- One stored file for the QA PDF in the `files` bucket (the object is not removed when the code is deleted). Remove it in Supabase Storage under your user id.
- Analytics totals for the account now include about 100 test scans in the all-time and monthly counters. If you want a clean baseline, reset the counters for your account in `qr_stats` and `scan_events` before real users arrive.
- The existing codes `Cafe toon`, `Cafe toon Wi-Fi`, `Home wifi`, `GITHUB` and `supabase.com` were not touched.

## Suggested order of work

1. Offer swap (item 1), WhatsApp number (item 4), template currency and the hard-coded "Table 4" (item 6): small, user-visible, low risk.
2. Visitor guard default (item 3): one setting, large effect for restaurants.
3. Cache staleness (item 2): needs a Worker change and a Worker deploy; add a QA section 15b check that an edit is visible on the next scan.
4. Sign-in branding (item 5): owner steps in Supabase and Google.
5. Count consistency (items 7 and 8), Place ID check (item 9), and the P2 and P3 lists.
6. Confirm the static-review items with a Free account.
